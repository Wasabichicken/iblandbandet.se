(i)Blandbandet API

A small JSON API for building external clients (e.g. a mobile app) against member accounts.

This is separate from the website itself, which stays a traditional server-rendered app using cookie-based sessions rather than this API's bearer tokens — the two use different auth mechanisms on purpose, not out of duplication.

Base URL

  • Production: https://www.iblandbandet.se/api/

Authentication

Call POST/api/login.cgi to get a token, then send it on every subsequent request:

Authorization: Bearer <token>

There's no separate CSRF token to manage — a bearer token has to be deliberately attached by client code, so it isn't vulnerable to the cross-site request forgery that cookie-based auth needs CSRF protection against in the first place.

Tokens don't expire on a schedule. Unlike the website's session cookies (30 days), an API token stays valid indefinitely until the client calls /api/logout.cgi to revoke it, or the member changes their password (see /api/me.cgi below, which revokes every other outstanding token on a successful password change). There's currently no way for a member to see a list of their own outstanding tokens.

All requests and responses are JSON. Send Content-Type: application/json on any request with a body.

POST/api/login.cgi

Request body:

{"email": "anna.lindqvist@example.invalid", "password": "hunter2"}

200 OK

{
  "token": "GlRMWCHZqVHYp2nk8f5DC_AGtnNVfpfhYwXbzbr5azA",
  "member": {
    "id": 39,
    "email": "anna.lindqvist@example.invalid",
    "instruments": "Klarinett",
    "description": "Lärare på mellanstadiet, spelar klarinett...",
    "is_active": true,
    "is_admin": false,
    "profile_picture": "/static/uploads/avatars/39_initials.svg"
  }
}

401 Unauthorized

{"error": "Fel e-postadress eller lösenord."}

Deliberately the same error for a wrong email and a wrong password — never reveals which one was incorrect.

GET/api/me.cgi

Requires a valid Authorization: Bearer header. No request body.

200 OK — the member fields directly (same shape as member above, not wrapped):

{
  "id": 39,
  "email": "anna.lindqvist@example.invalid",
  "instruments": "Klarinett",
  "description": "Lärare på mellanstadiet, spelar klarinett...",
  "is_active": true,
  "is_admin": false,
  "profile_picture": "/static/uploads/avatars/39_initials.svg"
}

instruments, description, and profile_picture can be null — a member isn't required to fill any of those in. A null profile_picture means "show a generic default image," the same as the website does.

401 Unauthorized — missing, malformed, or revoked token:

{"error": "Ogiltig eller saknad token."}

POST/api/me.cgi

Updates your own account. Two actions, same endpoint:

Update profile — request body:

{
  "action": "update_profile",
  "email": "anna.lindqvist@example.invalid",
  "instruments": "Klarinett, Saxofon",
  "description": "Lärare på mellanstadiet...",
  "is_active": true
}

200 OK with the updated member object (same shape as GET above). 409 Conflict if email is already taken by another member; 400 Bad Request if email is blank.

Change password — request body:

{
  "action": "change_password",
  "current_password": "old-password",
  "new_password": "new-password"
}

200 OK with {"ok": true}. 401 Unauthorized if current_password is wrong; 400 Bad Request if new_password is blank.

A successful password change revokes every other API token issued to this member — not the one used to make the request, so the device making the change stays logged in, but a token that leaked anywhere else stops working immediately. It doesn't touch the website's own session cookies.

POST/api/logout.cgi

Requires a valid Authorization: Bearer header. If the token is already invalid or missing, this still succeeds — there's nothing meaningful to report either way.

200 OK, always:

{"ok": true}

GET/api/calendar.cgi

Public — no token required. Lists every event, soonest first.

200 OK

[
  {
    "id": 1,
    "title": "Måndagsrep",
    "starts_at": "2026-09-07T16:45:00Z",
    "ends_at": "2026-09-07T18:30:00Z",
    "location": "Stallet, Umeå",
    "latitude": 63.8355172,
    "longitude": 20.262174,
    "description": null
  }
]

starts_at/ends_at are real UTC timestamps (note the trailing Z) — unlike the website's own calendar widget, which works with naive Stockholm-local times since it only ever runs in a browser in the same timezone the events were entered in, a general-purpose API client can't assume that, so these are always genuine UTC. ends_at, location, latitude, longitude, and description can all be null.

POST/api/calendar.cgi

Requires a valid Authorization: Bearer header. Any logged-in member can create, edit, or delete any event — there's no ownership or admin restriction on the calendar, matching how the website itself works.

Create — request body:

{
  "action": "create",
  "title": "Måndagsrep",
  "starts_at": "2026-10-05T19:00:00Z",
  "ends_at": "2026-10-05T21:00:00Z",
  "location": "Stallet, Umeå",
  "latitude": 63.8355172,
  "longitude": 20.262174,
  "description": null
}

Only title and starts_at are required. 200 OK:

{"id": 42}

Update — same body shape as create, plus "event_id": 42, with "action": "update". Delete — just {"action": "delete", "event_id": 42}. Both respond 200 OK with {"ok": true}.

400 Bad Request if title/starts_at are missing on create/update, or event_id isn't a number on update/delete. 401 Unauthorized if the token is missing or invalid.

GET/api/scores.cgi

Requires a valid Authorization: Bearer header for every request — unlike the calendar, nothing here is public. Browses the score archive: folders containing folders and files.

List a folder — pass ?path= followed by the folder's own path (see below for where that value comes from; omit it entirely for the archive's root). 200 OK:

{
  "path": "P%C3%A4rmen/9%20to%205",
  "breadcrumb": [
    {"name": "Pärmen", "path": "P%C3%A4rmen"},
    {"name": "9 to 5", "path": "P%C3%A4rmen/9%20to%205"}
  ],
  "entries": [
    {
      "name": "9 to 5.mscz",
      "path": "P%C3%A4rmen/9%20to%205/9%20to%205.mscz",
      "is_dir": false,
      "ext": ".mscz",
      "modified": "2026-09-01T06:19:20Z",
      "size": 1245010
    }
  ]
}

Each entry's path is already URL-encoded and ready to use as-is — pass it straight back as the next request's ?path=, whether you're descending into a folder or downloading a file. Folders have ext/size as null; only .pdf, .mp3, .mscz, and .txt files ever appear.

Download a file — same endpoint, path pointing at a file instead of a folder. The response isn't JSON in this case: it's the raw file bytes, with a real Content-Type and Content-Disposition (attachment for .mscz, since nothing can render it inline; inline otherwise).

404 Not Found for a path that doesn't exist. 401 Unauthorized for a missing/invalid token.

GET/api/chat.cgi

Requires a valid Authorization: Bearer header for every request — like scores, nothing here is public. A single shared chatroom, no channels: every member sees the same message history.

Two ways to send/delete text, both live-broadcast the same way — pick whichever fits. POST below and the WebSocket's message/delete types (see "WebSocket — live delivery" below) both end up persisting through this same endpoint, so it makes no difference to anyone else which one a client used. In practice: prefer the WebSocket while a client already has one open (no need to pay for a separate HTTPS request when there's already a live connection sitting there), and fall back to a plain short-lived POST when it doesn't - including for images, which can only ever go over POST — there's no way to send one over the socket.

List messages — no query params needed for the most recent history:

[
  {
    "id": 123,
    "member_id": 5,
    "body": "hej 👋",
    "image_id": null,
    "created_at": "2026-10-01T18:03:00Z",
    "profile_picture": "/static/uploads/avatars/5_initials.svg"
  }
]

Newest message first. Page backward through older history with ?before=<id> (the oldest id you've already seen); ?limit= caps how many come back (default 50, max 100). member_id and profile_picture can both be null — a message from a member who has since deleted their account still shows up in history, just with no sender to attribute it to.

There's no separate endpoint to look up a member's avatar. profile_picture rides along on every message directly, the same way it does everywhere else members' avatars are shown on the site — a deliberate choice to avoid a general "look up any member by id" endpoint that would tempt exposing more than an avatar (email, description) for someone other than yourself.

Fetch an image — ?image=<image_id>, using the image_id from a message that has one. Not JSON: the raw image bytes, with a real Content-Type sniffed from the file itself. 404 Not Found if the image doesn't exist (or was deleted along with its message).

POST/api/chat.cgi

Send a text message — request body:

{"action": "send", "body": "hej 👋"}

200 OK with the created message (same shape as the list above, image_id always null). 400 Bad Request if body is blank.

Send an image — same endpoint, but as multipart/form-data instead of JSON: an image file field, plus an optional body text field for a caption. Sending an image is sending a message — there's no separate upload-then-reference step, so there's no window where an uploaded file exists without a message pointing at it. 200 OK with the created message, image_id set to a value usable with ?image= above. 400 Bad Request if no file was attached or its bytes aren't a recognizable image format (JPEG/PNG/GIF/WEBP). 413 Payload Too Large above 10 MB.

Delete a message — request body:

{"action": "delete", "message_id": 123}

200 OK with {"ok": true}. 403 Forbidden if it's not your own message and you're not an admin — anyone can delete their own message, but only admins can delete someone else's. 404 Not Found if the message doesn't exist. 400 Bad Request if message_id isn't a number.

WebSocket — live delivery

wss://chat.iblandbandet.workers.dev/socket

New messages and deletions are pushed live over this socket — no polling needed. This isn't part of api/chat.cgi itself; it's a separate Cloudflare Worker that sits in front of it, relaying between connected clients and the same REST endpoint documented above.

Authenticate the same way as everywhere else — Authorization: Bearer <token> — but as a header on the WebSocket handshake request itself, not a query parameter. A connection missing or failing this check is rejected with 401 Unauthorized before the upgrade completes.

Browser JavaScript's WebSocket API can't attach custom headers to the handshake, so this requires a native client (or anything else that controls its own handshake) — not a plain browser tab. Every real client here is expected to be the mobile app itself.

Send a text message over the socket:

{"type": "message", "body": "hej 👋"}

Delete a message over the socket:

{"type": "delete", "id": 123}

The server confirms by broadcasting to every connected client, sender included — same shape as a row from GET above:

{
  "type": "message",
  "id": 123,
  "member_id": 5,
  "body": "hej 👋",
  "image_id": null,
  "created_at": "2026-10-01T18:03:00Z",
  "profile_picture": "/static/uploads/avatars/5_initials.svg"
}
{"type": "delete", "id": 123}

If a send/delete fails (blank body, deleting someone else's message, etc.), only the requester gets an error — nothing is broadcast:

{"type": "error", "message": "Du kan bara ta bort dina egna meddelanden."}
Images are still sent over the REST endpoint above, never the socket — the multipart/form-data upload described under POST. The socket only carries plain message/delete JSON. An uploaded image still broadcasts live to everyone connected, exactly like a text message does; it just gets there via a different path server-side, not something a client needs to think about.

History is REST-only — fetch it with GET above (paginated via ?before=) when the app opens or reconnects after being offline. The socket only ever carries new activity while connected, nothing retroactive.

Errors in general

  • 401 Unauthorized — not logged in / bad credentials / bad token.
  • 405 Method Not Allowed — wrong HTTP method (login.cgi and logout.cgi are POST-only).
  • All error bodies have the shape {"error": "<message>"}, with the message in Swedish, matching the rest of the site.

What's not here yet

Just the drive. Everything else on this page — login, identity (including editing your own profile and changing your password), the calendar, the score archive, and chat (including live delivery over the socket) — is implemented and live. A drive endpoint would be added the same way, reusing the existing bearer-token check for auth.
